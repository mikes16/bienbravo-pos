# Handoff T-049 — El cobro anuncia por qué no se pudo agregar un item del catálogo

## Interfaz expuesta
- `CheckoutPage` deja de descartar el retorno de `addCatalogItem`. El `onAdd` del
  `CatalogGrid` ya no es `(item) => ck.addCatalogItem(item)` sino `handleAddCatalogItem`:

  ```ts
  const handleAddCatalogItem = (item: Parameters<typeof ck.addCatalogItem>[0]) => {
    const result = ck.addCatalogItem(item)
    if (!result.added) addToast(result.message, 'error')
  }
  ```

  Genérico por diseño: vale para CUALQUIER `reason` de `AddCatalogItemResult`
  (`SERVICES_NOT_ALLOWED`, `NOT_ELIGIBLE`, `NEEDS_VARIANT` y los que vengan). El texto
  es el del hook — el POS no reimplementa la regla aquí.
- Canal del aviso: el toast de `@/core/toast` (`useToast().addToast`, variante `error`),
  el mismo que ya usaba `useCheckout` cuando una línea no entra por barbero excluido. Se
  consulta en tests con `screen.getByRole('status')` (raíz del `ToastViewport`, que
  `renderWithProviders` ya monta) y con el texto del mensaje.
- Sin cambios de firma para nadie: `useCheckout`, `addCatalogItem`, `CatalogGrid`,
  `CatalogTile`/`CatalogListRow` y `StaffSaleBar` quedaron intactos.

## Decisiones tomadas
- **Toast y no aviso junto a la StaffSaleBar**: en móvil el carrito es una hoja CERRADA
  mientras se toca el grid, así que un `role="alert"` dentro de `cartContent` quedaría
  fuera de pantalla justo en el momento del toque. El toast es fijo arriba y se ve en las
  dos disposiciones. Además el provider ya dedupe mensajes iguales dentro de 4 s, así que
  un spam-tap no apila avisos.
- **La página sólo anuncia**: no clasifica el `reason` ni escribe texto propio. Si mañana
  un `reason` nuevo necesita otra acción (p. ej. abrir el selector de presentación), se
  ramifica aquí sin tocar el hook.

## Advertencias para dependientes
- El aviso es del POS y es **previo al cobro**: no pasa por `rejectionNotice` ni por el
  banner de `ck.error` (el rechazo del API sigue por ahí, [D-039]).
- Un producto no elegible casi nunca llega a este camino: su card ya está `disabled`
  (T-032d). El caso vivo es el **servicio o combo** con `allowServicesInTicket === false`,
  que el grid no atenúa (`staffViews` sólo cubre productos).
- Quien aterrice T-033 (VariantPickerSheet) debe decidir si `NEEDS_VARIANT` abre el
  selector en vez de avisar: el punto de decisión es `handleAddCatalogItem`, un `if` sobre
  `result.reason` antes del `addToast`.
- Tests que afirmen "no salió ningún aviso" en checkout pueden usar
  `expect(screen.queryByRole('status')).not.toBeInTheDocument()`: hoy el único `role=status`
  de esta pantalla es el `ToastViewport` (el del `PaymentSheet` vive dentro del diálogo).
