# Handoff T-040 — Autenticar las 4 subscriptions del canal de frescura (hoy públicas)

## Interfaz expuesta
- **Contrato propuesto:** `createClient({ connectionParams: () => ({ authorization: 'Bearer <token>' }) })`
  en `src/core/apollo/client.ts:311` (`createPosApolloClient`). El POS manda un TOKEN DE CANAL corto,
  nunca la cookie de sesión.
- **Auditado: NO existe hoy ningún JWT accesible en el POS.** `usePosAuth`/`auth.repository.ts` sólo
  producen la cookie `bb_session_pos` (HttpOnly, opaca — verificado en
  `bienbravo-api/src/modules/auth/session-cookie.util.ts` y `auth.service.ts:117-130` `createWebSession`:
  token aleatorio, se guarda su hash en `AuthSession`, nunca se expone al JS). `PosViewer`
  (`src/core/auth/auth.types.ts`) no trae `accessToken`; grep de `token|jwt|bearer` en `src/` no da nada.
  Por T-035 esa cookie tampoco viaja en el upgrade WS de Safari/iPad. **Hace falta que el API emita un
  token de canal nuevo**, pedido por HTTP (donde la cookie SÍ funciona same-origin, comentario ~L244-250
  de `client.ts`) y guardado en memoria (store de módulo, nunca `localStorage`, como `saleActivity.ts` [D-032]).
- **Precedente exacto ya en el API** (solo lectura, no tocado): `bienbravo-api/src/modules/kiosk/kiosk-jwt.service.ts`
  — `signRotating({jti, locationId})` firma un JWT corto (900s) scoped a `locationId` con secreto propio;
  y `AuthService.createMobileTokens` (`auth.service.ts:172-196`) ya firma un JWT con `JwtService`/
  `JWT_ACCESS_SECRET`/`JWT_ACCESS_TTL_SECONDS` (900s default) — mismo mecanismo, nadie lo llama desde web/POS hoy.
  Propuesta: query nueva `posChannelToken(locationId: ID!): String!` protegida por la sesión STAFF actual +
  `assertLocationAllowed(viewer, locationId)` (`common/location-scope.ts:17`), TTL ~900s, refrescada
  proactivamente por el POS (igual que `signRotating`, no infinita).
- **Punto exacto a validar:** `api/src/main.ts:96-108` (`useServer`, función `context`) hoy sólo pasa
  `connectionParams` crudo sin verificar nada. Ahí debe: leer `connectionParams.authorization`, verificar
  el JWT (mismo secreto que la query), y si falta/es inválido **rechazar el connect completo** (graphql-ws
  permite lanzar en `context`/`onConnect`, cierra el socket para las 4 subscriptions de un golpe).
- **Guard por slug ↔ sucursal:** cada resolver ya recibe `@Args('slug')` pero lo ignora (`_slug`):
  `pos.subscription.resolver.ts:33` (`saleEvent`) y `:59` (`posDataChanged`),
  `booking.subscription.resolver.ts:29` (`appointmentUpdated`), `walkins.subscription.resolver.ts:31`
  (`walkInQueueUpdated`). El `locationId` decodificado del token debe adjuntarse al ctx en `main.ts` y
  compararse ahí contra `slug` — nótese que el `context()` actual NO cumple la forma `GraphQLContext`
  (falta `req`/`reply`), así que el guard no puede reusar `AuthService.getViewerFromContext` tal cual;
  necesita verificación directa tipo `KioskJwtService.verify`.

## Advertencias para dependientes
- **Orden de despliegue obligatorio:** (1) API agrega `posChannelToken` y dispara el guard en modo
  "acepta sin token" — el API acepta la credencial ANTES de exigirla; (2) POS empieza a pedirlo y mandarlo
  por `connectionParams` — el POS lo manda ANTES de que el API lo exija; (3) ventana de compatibilidad
  (mínimo un ciclo de deploy) para confirmar en logs 100% de conexiones con token válido; (4) API voltea
  el guard a exigir token válido + `locationId` == `slug`. Invertir el orden deja sin canal instantáneo a
  toda tablet en producción (degrada a reconexión con backoff de T-035, no crashea).
- El token viaja en el body JSON de `connectionParams`, visible/controlable por el JS del POS pase lo que
  pase con ITP: por eso es la única vía viable (T-035 ya documentó que la cookie del upgrade no llega en
  Safari/iPad) y no depende de arreglar el handshake.
- El token debe ser CORTO y re-mintable (orden de `JWT_ACCESS_TTL_SECONDS`, 900s): la tablet queda con la
  pestaña abierta días sin logout, así que un token de vida larga en memoria sería tan grave como filtrar
  la cookie de sesión.
