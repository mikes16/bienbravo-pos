# Handoff T-039 — recoverFromRejection: ningún rechazo del cobro se traga en silencio

## Interfaz expuesta
- `useCheckout()` — sin cambios de firma. Cambia el CONTRATO de
  `recoverFromRejection` (interno): **ningún** rechazo sale de ahí sin dejar
  algo en pantalla. Reparto vigente sobre `AnyCheckoutRejectionCode` ([D-039]):
  - recuperables (`PRICE_MISMATCH` / `BARBER_EXCLUDED` / `STOCK` /
    `REGISTER_SESSION_STALE`) → `rejectionNotice` (igual que antes, sin tocar);
  - `UNKNOWN`, cualquier código sin `locationId` y los tres `STAFF_SALE_*`
    (`_QUOTA_EXCEEDED` / `_NOT_ELIGIBLE` / `_VARIANT_REQUIRED`) → `error` con el
    mensaje en español del API tal cual. El carrito queda intacto, la hoja de
    pago sigue abierta y `submitting` vuelve a `false` por el `finally` de
    `submit` / `submitExtras`.
- El `switch` es **exhaustivo por compilador**: el `default` hace
  `const unhandledCode: never = code`. Agregar un miembro a
  `AnyCheckoutRejectionCode` rompe `npm run typecheck` en esa línea
  (verificado quitando un `case`: `TS2322 … is not assignable to type 'never'`).

## Decisiones tomadas
- Los `STAFF_SALE_*` van a `error` y **nunca** a `rejectionNotice`: [D-035] dice
  que el aviso es sólo para lo que el POS ya recuperó, y aquí no hay nada que
  recargar — lo resuelve el operador (elegir variante, quitar la línea) o el
  dueño (subir el tope). Así `CheckoutRejectionNotice` y `REJECTION_TITLE`
  siguen enumerando sólo los recuperables ([D-039]) y la UI no se tocó.
- El `switch` narrowea sobre un `const code: AnyCheckoutRejectionCode =
  rejection.code`, no sobre la propiedad: el chequeo de exhaustividad no puede
  depender de que TS conserve el narrowing de una propiedad entre `await`s.
- El `default` usa `const … : never = code` y no `code satisfies never`:
  `@typescript-eslint/no-unused-expressions` viene en la config `recommended`
  del repo y marcaría la segunda forma. El `never` se lee en el `setError`
  (`${detail} (${String(unhandledCode)})`), así que tampoco hay `no-unused-vars`.

## Advertencias para dependientes
- **Quien encienda el modo venta a staff en la UI ya no tiene que dar salida a
  esos tres códigos**: el hook los pinta. Lo que sí falta es la UX fina (p. ej.
  abrir el selector de variante ante `STAFF_SALE_VARIANT_REQUIRED` en vez de
  sólo mostrar el texto del API) — eso es trabajo de presentación, no del hook.
- **Un código nuevo en `AnyCheckoutRejectionCode` no compila** hasta que se le
  agregue `case` en `recoverFromRejection`. Es intencional: decide si es
  recuperable (`rejectionNotice`, y entonces también entra a
  `CheckoutRejectionCode` + `REJECTION_TITLE`) o no (`error`).
- El marcador estable de "hay `rejectionNotice`" en tests es el texto
  **"Toca Cobrar para continuar"** (sólo lo emite ese bloque); el `message` del
  aviso no sirve para distinguirlo porque en `STOCK` es el texto del API.
- Los mensajes del API en los tests nuevos son fixtures, no contrato: el texto
  real lo manda `bienbravo-api` y el POS lo muestra tal cual ([D-040]).
