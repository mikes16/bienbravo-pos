# Handoff T-011 — FreshnessProvider montado en la app y refresco al desbloquear con PIN

## Interfaz expuesta
- `src/app/Providers.tsx`
  - El árbol real es `Apollo → Repositories → Location → PosAuth → **FreshnessGate** →
    Bootstrap → Toast → children(router)`. **Ya no hace falta montar nada**: cualquier
    pantalla del POS puede usar `useLiveRefresh(load, topics)` / `useFreshness()`.
  - `FreshnessGate` (privado) monta `<FreshnessProvider>` **solo con sesión**
    (`isAuthenticated`, o sea `viewer !== null`). Sin sesión NO hay contexto: quien llame
    `useFreshness()` fuera del árbol autenticado sigue lanzando. `lock()` conserva el
    viewer ⇒ bloquear no desmonta el canal.
  - `export function RefreshOnUnlock()` — componente sin UI (devuelve `null`) que observa
    `isLocked` con un ref del valor previo y llama `refreshAll()` en la transición
    true → false. Ya va montado dentro de `FreshnessGate`; se exporta para poder
    montarlo/probarlo (lo usa `PosShell.test.tsx`). Requiere `PosAuthProvider` +
    `FreshnessContext` arriba.
- `src/app/PosShell.tsx` — la barra recibe
  `trailing={<RefreshControl timezone={locationTimezone} />}`: el control "Actualizar
  datos" ya se ve en TODA pantalla del shell (`getByRole('banner')` →
  `getByRole('button', { name: 'Actualizar datos' })`).
  **Actualizado por T-025**: entre `<main>` y `<BottomTabNav>` va ahora
  `<AutoLockWarning />` (fila propia, sólo visible en los últimos 5 s).
  **Actualizado por T-027**: en ese mismo hueco y ARRIBA de `<AutoLockWarning />` va la
  franja "Hay una versión nueva…" (`DeployUpdateNotice`, local al archivo) que enciende
  `useDeployWatcher()`; sólo se ve con venta en curso — en cualquier otro caso el POS se
  recarga solo. El shell es además el disparador "al desbloquear" del watcher: se monta
  con cada desbloqueo.

## Decisiones tomadas
- **Gate por sesión con montaje condicional** (no un flag interno: `FreshnessProvider` está
  fuera del alcance). Hace falta porque la sucursal se resuelve con una query pública
  (`posPublicLocations`): un POS deslogueado tiene `locationSlug` y, sin gate, sostendría
  las 3 suscripciones con cookie muerta. Costo asumido: cuando `viewer` pasa de null a no
  null (login) o al revés (logout) el subtree —router incluido— se re-monta una vez. No
  ocurre al bloquear/desbloquear, que es el camino diario.
- **El observador del desbloqueo vive en `Providers.tsx`, no en `PosShell`**: con el POS
  bloqueado la ruta es `/` (lock screen) y `PosShell` está DESMONTADO, así que desde el
  shell la transición nunca se vería. Tampoco en `PosAuthProvider` (no se acopla auth a
  frescura).
- **El reloj de pared del shell dejó de usar un temporizador periódico**: timeouts de una
  sola vez encadenados (misma cadencia de 30 s, cero red), alineado con [D-015].
- **Los dos tests del shell usan un `FreshnessContext.Provider` de mentira** (inerte, con
  `refreshAll` espiado) en vez del provider real: con el real, `MockedProvider` recibiría
  3 suscripciones sin mock. `renderWithProviders` NO se tocó.

## Advertencias para dependientes
- Las pantallas que migren a `useLiveRefresh` deben quitar sus suscripciones propias
  (`HoyPage`, `MyDayPage`, `DaySalesPage` siguen abriendo las suyas: hoy hay 3 operaciones
  extra en el socket, sin doble refresco porque el provider no registra cargadores ajenos).
- Todo test que renderice `PosShell` necesita un `FreshnessContext.Provider` arriba
  (copia `INERT_FRESHNESS` de `PosShell.cajaGate.test.tsx`) y, desde T-025, un
  `vi.mock` de `useAutoLock` o pedirá `posSettings` sin mock.
- `refreshAll()` ignora la ventana de 5 s: sigue prohibido colgarlo de un temporizador. El
  único disparador por acción que existe hoy es el desbloqueo; "entrar a Nueva venta"
  (spec § 3.3 d) todavía falta.
- `BootstrapProvider` quedó DENTRO del gate: ya puede usar `useLiveRefresh` para la versión
  de catálogo al desbloquear (§ 3.4/3.6) sin mover nada.
- `RefreshControl` se paga en el bundle inicial (va en el shell): `npm run size` quedó en
  95.45 kB de 105 kB de presupuesto.
