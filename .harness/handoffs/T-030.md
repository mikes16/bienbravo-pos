# Handoff T-030 — Reglas de presentación de la venta a staff en el carrito

## Interfaz expuesta
`src/features/checkout/lib/staff-sale.ts` (puro: sin UI ni red, todo en centavos enteros):

- `staffLineView(product: CatalogProduct, variantId: string | null = null): StaffLineView`
  → `{ eligible, reason?: 'NOT_ELIGIBLE' | 'NEEDS_VARIANT', unitPriceCents: number | null,
  listUnitPriceCents: number }`. `unitPriceCents` es **null** cuando no hay precio que
  pintar (no elegible o falta presentación): nunca 0. `listUnitPriceCents` sale de la
  variante elegida y, sin variante, de `product.priceCents` (= el de la 1ª variante, ver
  repo). Un `variantId` desconocido cuenta como "ninguna elegida".
- `needsVariant(product): boolean` — true con >1 variante y precios staff **o** públicos
  distintos entre ellas (el público importa porque el tope de monto se mide ahí).
- `staffCartSummary(lines): { listTotalCents, staffTotalCents, discountCents }` —
  `discountCents` nunca negativo.
- `quotaView(quota: StaffSaleQuota, cartLines): StaffQuotaView` →
  `{ units, listAmountCents, perProduct[], exceeded }`; cada tope es
  `{ used, inCart, limit, remaining, exceeded }`. `limit: null` ⇒ `remaining: null` y
  `exceeded: false` siempre. `remaining` es **después del carrito** y puede ser negativo
  (el excedente). `perProduct` trae un renglón por producto del carrito, en orden de
  aparición.
- `STAFF_SALE_MESSAGES`, `staffLineMessage(view): string | null`,
  `unitsQuotaMessage(units): string | null` → textos es-MX listos. **Actualizado por
  T-050:** el texto de `NEEDS_VARIANT` es INTERINO (manda a cobrar fuera del modo staff:
  no hay selector de presentación); T-033 lo revierte. Código y regla ([D-042]) intactos.
- `StaffSummaryLine { kind; itemId; qty; unitPriceCents; listUnitPriceCents?: number | null }`
  — subtipo estructural de `CartLine`: un `CartLine` con `listUnitPriceCents` encaja.

**Contrato clave:** una línea cuenta como venta a staff ⇔ `kind === 'product'` **y**
`listUnitPriceCents != null`, igual que en el API (`SaleItem.listUnitPriceCents` solo se
llena en venta a staff, spec §4.1). Quien conecte el carrito debe congelar ese precio
público en la línea al agregarla; sin él la línea se trata como venta normal.

## Decisiones tomadas
- `NOT_ELIGIBLE` gana sobre `NEEDS_VARIANT`: si el admin apagó el producto, elegir
  presentación no lo arregla.
- `remaining` **no** se recorta a 0 cuando se excede: la UI necesita el excedente para el
  aviso. `exceeded ⇔ remaining < 0`; llegar justo al límite NO excede.
- `quotaView` respeta el `*Remaining` que manda el API cuando existe (una anulación
  devuelve cupo y la resta `limit − used` no siempre cuadra); solo lo deriva si viene null
  con tope no nulo.
- `unitsQuotaMessage` cuenta el mes **más** el carrito ("lo que quedaría al cobrar"); con
  carrito vacío coincide con lo que reporta el API.
- `perProduct` se arma sobre los productos del CARRITO, no sobre `quota.unitsByProduct`: es
  la lista que la UI necesita para bloquear, y un producto sin renglón en el cupo cuenta
  como 0 usado.

## Advertencias para dependientes
- **Nada de esto decide**: `createPOSSale` vuelve a medir precio, elegibilidad y topes en
  su transacción (spec §4.3). `exceeded` solo sirve para deshabilitar Cobrar con mensaje;
  si el API rechaza igual, se muestra su texto (`StaffSaleRejectionCode`, handoff T-029).
- `quota.enabled` y `quota.allowServicesInTicket` **no** se consultan aquí: el interruptor
  de venta a staff y el gate de servicios en el ticket son de quien monte la UI.
- El módulo no toca `CartLine` ni el reducer: agregar `listUnitPriceCents` a la línea (y
  mandar `productVariantId` cuando `needsVariant`) es trabajo de la tarea que conecte el
  carrito.
