# Handoff T-058 — Corte de caja: el contado de Stripe sigue al esperado vivo

## Interfaz expuesta
- `CloseCajaWizard` (sin props, misma ruta `/caja/cerrar`, mismos 3 pasos). Lo que cambió es
  de dónde sale el contado digital:
  - **Stripe / transferencia**: ya NO vive en estado. Se DERIVA en render
    `const countedTransferCents = session?.expectedTransferCents ?? null`. Se fue el
    `useEffect` de auto-relleno con guarda `=== null` (y con él la constante
    `PENDING_DIGITAL`). El payload de `closeSession` manda el `countedTransferCents` VIGENTE
    al tocar "Cerrar caja", no el del primer render con sesión.
  - **Tarjeta**: sigue capturada a mano, ahora en su propio estado
    `const [countedCardCents, setCountedCardCents] = useState<number | null>(null)`. Confirmar
    el esperado o "Ajustar" funciona igual, y una lectura nueva de la caja NO la pisa.
  - `ConfirmDigitalStep` **no se tocó**: sigue recibiendo
    `counted: DigitalCounted = { cardCents: countedCardCents, transferCents: countedTransferCents }`
    (objeto armado en render) y su `onChange` sólo guarda `next.cardCents` — el canal de
    Stripe no tiene control que lo edite.
  - `canAdvance` en el paso 2 es el mismo booleano (`cardCents !== null && transferCents !== null`):
    con sesión, transfer nunca es null, así que lo único que traba sigue siendo la TARJETA.
- Sin cambios en: pasos, conteo de efectivo, `ReviewCloseStep` (el diff de transferencia ahora
  es 0 por construcción), rebote a `/caja`, splash de éxito, ramas de permiso / carga fallida /
  esqueleto ([D-018]/[D-060] intactas: sin `session` el wizard no arranca y no pinta $0).
- Tests: `registersWith(overrides)` en `CloseCajaWizard.test.tsx` arma otra lectura de la MISMA
  caja con montos distintos; el escenario "otra terminal cobró" es
  `current = registersWith({...})` + `await announce('sales')` (el `announce` de
  `renderWithProviders`, con `getRegisters` mockeado como `vi.fn(async () => current)`).

## Decisiones tomadas
- Se eligió DERIVAR en render en vez de "sincronizar el estado en cada cambio de `session`":
  un contado que nadie puede editar no es estado, y así no hay ventana entre el render con el
  esperado nuevo y el efecto que lo copiaría (el submit lee siempre lo vigente).
- El estado del paso digital se partió en dos (`countedCardCents` capturado + transfer
  derivado) en vez de mantener el objeto `DigitalCounted` en `useState`: el objeto se sigue
  armando en render para no cambiar la firma de `ConfirmDigitalStep`, que está fuera de alcance.
- No se agregó fila ni input de Stripe: sigue siendo auto-confirmado por definición (el cajero
  no tiene contra qué reconciliarlo); el fix es que lo auto-confirmado sea la cifra de ahora.

## Advertencias para dependientes
- **Sigue abierto (Minor del Principal, fuera de alcance)**: `ConfirmRow` de
  `steps/ConfirmDigitalStep.tsx` siembra su input con `expected` UNA vez al montar y su
  comentario "expected is static for a given close-caja session" es falso — si
  `expectedCardCents` se mueve a media captura, un "✓ Confirmado" viejo queda desalineado del
  esperado nuevo y nada lo señala. Esta tarea FIJA ese comportamiento con un test ("la tarjeta
  ajustada a mano NO se pisa"): quien agregue el aviso visual de desalineación no debe
  auto-pisar la captura del cajero, sólo marcarla.
- El warning `react-hooks/set-state-in-effect` que T-016d/T-044 documentaban en este archivo ya
  no existe (desapareció con el efecto): `npx eslint src/features/register/presentation/CloseCajaWizard.tsx`
  sale exit 0 sin salida. `steps/ConfirmDigitalStep.tsx` conserva su error de lint pre-existente,
  así que el check de lint se sigue acotando al wizard.
- Quien toque el payload de `closeSession`: `countedTransferCents` ya no puede diferir del
  esperado (diff siempre 0). Si algún día el API exige un contado de Stripe distinto del
  esperado, hay que agregarle UI al cajero antes — hoy no habría cómo corregirlo.
