# Handoff T-029 — Repositorio de cobro: precio staff, cupo del barbero y venta a staff

## Interfaz expuesta
- `checkout.types.ts` (nuevos exports):
  - `CatalogProductVariant { id; priceCents; staffPriceCents: number | null }` y
    `CatalogProduct` ahora trae `staffSaleEligible: boolean`,
    `staffPriceCents: number | null` (resuelto por el API) y `variants[]`.
    `staffPriceCents === null` = **no vendible a staff** (nunca $0).
  - `StaffSaleQuota` / `StaffSaleProductUnits`: cupo del mes. Un límite o
    restante en `null` = **sin tope**, jamás cero.
  - `StaffSaleInput { buyerStaffUserId }`; `CreateSaleInput.staffSale?` y
    `SaleItemInput.productVariantId?` (ambos opcionales).
  - `StaffSaleRejectionCode` = `STAFF_SALE_QUOTA_EXCEEDED` |
    `STAFF_SALE_NOT_ELIGIBLE` | `STAFF_SALE_VARIANT_REQUIRED`, y
    `AnyCheckoutRejectionCode = CheckoutRejectionCode | StaffSaleRejectionCode`.
    `CheckoutRejectedError.code` y `checkoutRejectionCodeFrom()` devuelven el
    tipo ancho; conservan el mensaje en español del API tal cual.
- `CheckoutRepository` — **método nuevo obligatorio**:
  `getStaffSaleQuota(locationId, buyerStaffUserId?) => Promise<StaffSaleQuota>`.
  Siempre `network-only` y **sin** parámetro de política de fetch ([D-017]).
  Sin `buyerStaffUserId` manda `null` = el de la sesión (lo resuelve el API).
- `createSale(input)`: si `input.staffSale` viene, manda
  `staffSale: { buyerStaffUserId }` y el `productVariantId` de cada línea que lo
  traiga. **Sin `staffSale` el payload es el de antes** (ninguna llave nueva).
- `getProducts()` pide `staffSaleEligible` + `staffPriceResolvedCents` (producto
  y variante); el POS **no** pide el costo crudo en ningún momento.

## Decisiones tomadas
- Los 3 códigos de venta a staff van en su **propia** unión y NO dentro de
  `CheckoutRejectionCode`: ese tipo es el de los rechazos RECUPERABLES y lo
  enumeran exhaustivamente `CheckoutRejectionNotice` y el `REJECTION_TITLE` de
  `CheckoutPage` (fuera de mi alcance). Ensancharlo rompía el typecheck de
  presentación y, peor, prometía una recuperación automática que no existe.
- El tope excedido llega con código propio (`STAFF_SALE_QUOTA_EXCEEDED`); "no
  elegible" y "falta variante" llegan como `BAD_USER_INPUT` y se reconocen por
  el mensaje. Aquí sí es seguro en producción (a diferencia de STOCK): son
  `GraphQLError` con `extensions.code`, que el filtro del API devuelve intacto.
  Los códigos tipados ya se aceptan por si el API los estrena.
- `staffSaleQuota` se deja **sin clasificar** en `core/apollo/dataClasses`: la
  lista de permitidos ([D-003]) ya impide que se persista. Clasificarlo como
  SENSIBLE es de la tarea de `useCheckout`, junto con el evict al bloquear.

## Advertencias para dependientes
- **Hueco abierto a propósito:** `recoverFromRejection` (useCheckout) hace
  `setError(null)` y luego un `switch` sin `default`; un rechazo de venta a
  staff cae fuera y **no pintaría nada**. Hoy es inerte (nadie manda
  `staffSale`), pero quien encienda el interruptor DEBE darles salida —
  mostrarlos como aviso no recuperable— en el mismo cambio.
- El cupo se lee al abrir/cambiar comprador, no en bucle (cada llamada es un
  round-trip) y es sólo display: `createPOSSale` lo vuelve a medir.
- `staffPriceCents` de producto y de variante pueden diferir: si difieren entre
  variantes, la línea DEBE mandar `productVariantId` o el API la rechaza.
- Un repositorio de checkout nuevo debe implementar `getStaffSaleQuota()`.
- **Actualizado por T-036:** la contraposición "aquí sí es seguro en producción,
  a diferencia de STOCK" sigue vigente y ahora está escrita en los docstrings de
  `rejectionCodeFromMessage` / `STOCK_MESSAGE_PATTERN` (checkout.types.ts): la
  clasificación por texto vale para los rechazos de venta a staff porque llegan
  como `GraphQLError` ([D-040]); para STOCK es respaldo sólo de desarrollo hasta
  que el API mande `INSUFFICIENT_STOCK` (ver `.harness/handoffs/T-036.md`).
