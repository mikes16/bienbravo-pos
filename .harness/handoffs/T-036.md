# Handoff T-036 — Rechazo por STOCK: el código del API es la ruta de producción

## Interfaz expuesta
- `checkoutRejectionCodeFrom(code, message)` (`domain/checkout.types.ts`) **ya
  aceptaba** `extensions.code: 'INSUFFICIENT_STOCK'` → `'STOCK'` conservando el
  `message` en español del API: no hizo falta ensanchar el `switch`. Ninguna
  firma ni export cambió; nada que re-importar.
- `CheckoutRejectedError` sigue siendo `{ code, message }`: los faltantes **no**
  viajan en el error — `useCheckout.reloadStockAndFindShortages` los recalcula
  contra el stock que responde el API (T-026). Lo que el API mande de más en
  `extensions` (p.ej. `shortages`) se ignora sin alterar el mapeo (hay test).
- `STOCK_MESSAGE_PATTERN` queda documentado como respaldo **sólo de desarrollo**;
  la clasificación por texto sigue siendo vía válida para los rechazos de venta
  a staff, que sí llegan como `GraphQLError` ([D-040]).
- Helper de test `makeClientRejectingWith(message, code?, extras?)`: `extras` se
  mezcla dentro de `extensions` para simular payloads ricos del API.

## Decisiones tomadas
- **Cero cambio de comportamiento en el POS**: el hueco es del API y el POS ya
  está listo. Esta tarea arregla la documentación (prometía una recuperación
  por texto que producción no da) y la cobertura del caso real.
- No se agregó `shortages` a `CheckoutRejectedError`: sería un campo sin
  consumidor (`useCheckout` recalcula contra el stock del API, que es el dato
  fresco). El test sólo fija que un `extensions` rico no rompe el mapeo.
- El test del caso enmascarado se dejó **verde afirmando `UNKNOWN`**, con el
  porqué en el nombre: documenta el estado vigente, no lo bendice.

## Advertencias para dependientes
- **Cambio que necesita `bienbravo-api` (repo independiente, NO aplicado desde
  aquí)** — sin él, el rechazo más frecuente del cobro sigue cayendo en
  `UNKNOWN` en producción (banner genérico, sin recarga de existencias):
  - Archivo: `src/modules/pos/pos.resolver.ts`, método privado
    `assertStockAvailable` (~L751); el `throw` de los faltantes está al final
    (~L784). Lo usan `createPOSSale` (~L1553) y la venta de cita (~L2293): un
    solo cambio cubre ambas mutations.
  - Sustituir `throw new Error(...)` por `GraphQLError` (import de `graphql`)
    **conservando el texto actual en español** (el POS lo muestra tal cual):
    `throw new GraphQLError(mensajeActual, { extensions: { code:
    'INSUFFICIENT_STOCK', shortages: [{ productId, name, availableQty,
    requestedQty }] } })`. `shortages` es opcional para el POS.
  - Por qué funciona: `src/common/graphql-exception.filter.ts` devuelve intacto
    cualquier `GraphQLError` (`catch()`, ~L29); un `Error` pelón pasa por
    `normalize()` y con `NODE_ENV === 'production'` su mensaje se reemplaza por
    `'Internal server error'` con código `INTERNAL_SERVER_ERROR` (~L85).
  - No basta adjuntarle `extensions` a un `Error` pelón: el filtro rescata el
    `code` y el mensaje, pero reconstruye el error y **pierde** los extras.
  - Opcional (solo REST): `codeToStatus` del filtro manda a 500 los códigos que
    no enumera; agregar `INSUFFICIENT_STOCK → 409` si se quiere status correcto.
    GraphQL no depende de eso.
  - Tras aplicarlo en el API: no hay nada que tocar en el POS; sí conviene
    borrar `STOCK_MESSAGE_PATTERN` y su respaldo, y voltear el test
    "STOCK enmascarado en PRODUCCIÓN cae en UNKNOWN".
- Los tests de `CheckoutPage` simulan STOCK con `new Error('Stock insuficiente:
  …')`: si se borra el patrón, esos mocks tienen que pasar a mandar el código.
