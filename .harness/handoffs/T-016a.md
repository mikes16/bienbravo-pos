# Handoff T-016a — Canal de frescura: tema 'register' y stub de frescura en renderWithProviders

## Interfaz expuesta
- `src/core/freshness/FreshnessProvider.tsx`
  - `type FreshnessTopic = 'sales' | 'walkins' | 'appointments' | 'register'`.
  - `FRESHNESS_TOPICS = ['sales', 'walkins', 'appointments', 'register']` (orden estable; `'register'` al final).
  - `useLiveRefresh(load, ['register'])` ya compila y se registra como cualquier otro tema.
  - **`EVENT_SOURCES` sigue con 3 entradas a propósito**: el API todavía no publica el evento de caja
    (spec 3.3 c). Hoy `'register'` se dispara por reconexión, foco/`visibilitychange` y `refreshAll()`,
    que usan `FRESHNESS_TOPICS` completo. Está documentado en el docblock de `FreshnessTopic`.
- `src/test/helpers/renderWithProviders.tsx`
  - Monta por default un `FreshnessContext.Provider` **stub** alrededor del `ui`
    (`connection: 'connected'`, `lastUpdatedAt: null`, `refreshAll`/`setPaused` no-op, `register` real
    que guarda los cargadores). Ya no hace falta envolver a mano una pantalla con `useLiveRefresh`.
  - Devuelve, junto al `RenderResult`, `announce(topic: FreshnessTopic): Promise<void>` — corre dentro de
    `act` los cargadores registrados en ese tema con `Promise.allSettled`:
    ```ts
    const { announce } = renderWithProviders(<CajaPage />)
    await announce('register')
    ```

## Decisiones tomadas
- **Tema sin fuente de eventos, a propósito.** No se agregó entrada a `EVENT_SOURCES` ni suscripción
  nueva: la que emitirá `'register'` llega en una tarea del API. El docblock lo dice para que nadie lea
  la lista de 3 como un olvido.
- **El stub va dentro de `ToastProvider` y sólo envuelve `{children}`**: un test que necesite otro estado
  del canal (sin conexión, espiar `refreshAll`) monta SU provider alrededor del `ui` y gana por
  anidamiento. `DaySalesPage.test.tsx`, `MyDayPage.test.tsx`, `HoyPage.test.tsx`, `PosShell*.test.tsx` e
  `IdentityStripV2.test.tsx` siguen con el suyo, sin tocarse.
- **El valor del stub se crea UNA vez por llamada a `renderWithProviders`** (fuera del `Wrapper`): con un
  objeto nuevo por render, el `useEffect` de `useLiveRefresh` re-registraría en bucle.
- No se montó el `FreshnessProvider` real en el helper: abriría 3 suscripciones contra `MockedProvider`.

## Advertencias para dependientes
- **`announce(topic)` sólo corre lo registrado en ESE tema.** Una pantalla registra una carga por clase
  de dato ([D-019]): Caja debe avisar `'register'` para su corte y `'sales'` si además muestra ventas.
- **Un aviso = una consulta de red más** (las pantallas de dinero van `network-only`, [D-017]): el mock de
  Apollo necesita `maxUsageCount > 1` o fallará con "no more mocked responses" en el segundo refresco.
- Si agregas otro tema: amplía el tipo, `FRESHNESS_TOPICS` y `lastRunAt` del motor (el typecheck sólo
  obliga en el último) y ajusta el caso `'register' es parte de todos los temas, en orden estable`
  de `FreshnessProvider.test.tsx`, que asierta la lista completa.
- `'register'` no se refresca al cobrar: el evento `saleEvent` es del tema `'sales'` y no lo arrastra
  (hay un test que lo fija). Mientras el API no publique el evento de caja, otra terminal que abra o
  cierre caja no actualiza a ésta hasta una reconexión, foco o "Actualizar".
